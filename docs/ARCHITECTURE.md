# Architecture

Two processes that can't talk to each other directly, and how they do anyway.

```
   WoW client (Lua sandbox)                        bridge.js (Node, same machine)
   ┌──────────────────────────┐                    ┌─────────────────────────────┐
   │ ClaudeWoW addon              │  pixels on screen  │ Screenshot() -> decode.js   │
   │  draws message strip ────┼───────────────────▶│  screen-captures the corner │
   │                          │                    │  decodes → {session,chat,id,│
   │                          │                    │            cwd,flags,name,  │
   │                          │                    │            text}            │
   │                          │                    │        │                    │
   │                          │                    │        ▼                    │
   │                          │                    │  claude / codex / grok / …  │
   │                          │                    │   (per chat, parallel,      │
   │                          │                    │   resumed; agents.js)       │
   │                          │                    │        │                    │
   │  LoadAddOn(ClaudeWoW_S…)     │  files on disk     │        ▼                    │
   │  ◀───────────────────────┼────────────────────┤  writes 200 slot Inbox.lua  │
   │  PlaySoundFile(sig/…)    │                    │  deletes armed signal wavs  │
   └──────────────────────────┘                    └─────────────────────────────┘
```

## The sandbox

WoW addons cannot open sockets, read files, run programs or receive input from other processes. What they *can* do that reaches outside:

1. Draw pixels. Anything on screen can be captured by another process.
2. Load files that already existed when the client launched, the first time each is used. Files created after launch are not discovered. A file that was already loaded keeps returning the cached content for the rest of the process, even across `/reload` (fonts, sounds, textures) — except addon **Lua code**, which is re-read on `/reload`. These rules were measured on a live Forever client by [wow-forever-codex](https://github.com/0xinuarashi/wow-forever-codex) and match what this project observes.
3. Write SavedVariables — but only on `/reload` or logout, and `ReloadUI()` can only be called from a hardware event (a key or click), never from a timer.

Everything below follows from those three facts.

## Outbound: the pixel strip

Two transports carry the strip out, chosen by `capture.mode` in the bridge config and named to the addon in every slot file. **`screenshot`**, the default, is described under [The screenshot transport](#the-screenshot-transport): the addon calls `Screenshot()` with the strip up and the bridge decodes the file. **`pixel`**, described first because the strip's encoding was designed for it, screen-captures the strip continuously with `capture.ps1` / `capture_mac.py` / `capture_x11.py`; it is deprecated, kept only until `Screenshot()` is confirmed on Windows and on Linux under Wine, and it is what the bridge falls back to on its own when the addon reports that it cannot shoot (`shot=missing`: no `Screenshot()` in the client; `shot=failed`: `SCREENSHOT_FAILED` on every try; `fallbackToPixel` in `bridge.js`, remembered as `transportFallback` in `state.json` and named in the slot files as `transportNote`, which `/claude diag` shows). The encoding is the same on both.

`Codec.lua` turns a message into a byte stream and packs it into 3-bit cells:

```
[0xC7 0x1A] [id hi, lo] [len hi, lo] [payload…] [Fletcher-16 s1, s2]
```

Each cell is a 4×4-pixel square drawn with `SetColorTexture`, each channel fully on or off (8 colors). Pure primaries survive any gamma/contrast setting, unlike intermediate levels (a first version used 4 levels per channel and misread under some display settings). 200 cells per row, up to 48 rows, anchored at the top-left of `UIParent` with the frame scaled to `768 / physicalScreenHeight` so one UI unit is exactly one pixel. Capacity ≈ 3.2 KB per frame. That is codec 1, the capture scripts' strip; the screenshot transport's denser codec 2 (2 px cells, four levels a channel, magic `C7 2A`) is described under that transport.

The payload is one or more records separated by `\x1E`, fields by `\x1F`:

```
session \x1F chat \x1F id \x1F cwd \x1F flags \x1F name \x1F [context \x1F] text
```

- `session` — a random token generated when the addon's saved data is created. Message ids restart if the client wipes saved data; the bridge dedups on `(session, id)`.
- `flags` — `n` = start a fresh agent session; `h` = hello (announce the session token, no prompt; it also carries `ver=<the addon's semver>` and `proto=<the addon's wire protocol>`, see [Version handshake](#version-handshake)); `d` = the chat was deleted in game: drop its transcript and agent session, no prompt (the addon keeps the id in `db.forget` and resends it with each hello until the bridge acks); `c` = a game-context field sits between `name` and `text`; `allow=Rule1,Rule2` = add permission rules before running; `once=Rule1,Rule2` = allow these rules for this one run without saving them (Greed on the roll frame; `allowOnce` in the reload outbox); a folder the reply denied as `AddDir(<folder>)` never rides in `allow=` or `once=`: Need adds it to the chat's `dirs=` for good and Greed adds it to that one message's `dirs=`; `agent=codex` = run this chat with that agent instead of the bridge's default (absent for chats on the default); `plugin=<id>` = the chat's plugin (the addon sends `claude-code` for a chat with a folder and `live` for a chat attached to a running session, nothing otherwise); the per-chat settings from the `/claude` flags, `model=<name>`, `effort=<level>`, `pm=<permission mode>` and `dirs=<hex of the --add-dir folders, separated by US>`; `resume=<session id or prefix>` = adopt that session for this chat before running (sent once, after `/claude -r`; the bridge looks it up in its own sessions, then in Claude Code's `projects/` folder, and answers an unknown or ambiguous one with an error reply); `live=<hex of a session id or name>` = send this chat to that running session only. The reload outbox stores the allow list as hex text separated by `US`, so `/reload` preserves the same permission grant, and the new tokens as hex in its `opts` field.
- `context` — only present with the `c` flag (so a separator inside the text can't be mistaken for it): a few lines about the game, character, zone, map coordinates, money, talents, professions and quest log ids (`ClaudeWoW.GameContext()`, capped at 900 bytes; since coordinates change as you move, most messages sent after walking somewhere carry a fresh copy). Every hello carries it (empty when `/claude config context off`); a message carries it only when it differs from the last version the bridge acknowledged, and only if it fits next to the text.
- `text` — the message. Item, spell, quest and recipe (`enchant`) links the player shift-clicked in (`|Hitem:2140:…|h[Fine Longsword]|h`) are expanded before sending: `[Fine Longsword]` stays in the text and the link's tooltip, read off a hidden `GameTooltip` via `SetHyperlink`, is appended in a `--- Linked from the game ---` block.

The strip stays up until the bridge acknowledges the message (see signals) or 40 s pass, then it is re-shown up to three times before the addon gives up on pixels and arms the reload fallback for that message.

### Game state records (`kind=gs`)

`Telemetry.lua` sends the character's game state as quiet records: `session, "", seq, "", "kind=gs", character, text`. The name field holds the character key, the same one `bridge/goals.js` (`characterOf`) reads off the context's Character line: the addon builds that line with `ClaudeWoW.CharacterLine()`, the same function `GameContext()` uses, and applies the same rules (the first word of the name; the realm cut at the first `,` or `(`, trimmed, whitespace removed; no realm, just the name; letters, digits, `_` and `-` only; at most 64 characters), so `Bone-Forever`. Lua cannot tell non-ASCII letters from other non-ASCII characters, so it keeps every non-ASCII byte; a name or realm with a non-ASCII character that is not a letter gives a key the bridge refuses. The bridge logs each refused key once and lists it in the slot field (`refused`), and an addon whose key is listed stops sending. A record is filed under the character that sent it, never under whatever context the bridge heard last, and in the same folder as that character's `goals.json`. Known limit, as for the Orders card: two characters on one realm whose names share a first part share a folder. The id field holds the record's own sequence (`max(last + 1, time())`, so a crash that loses the saved counter never goes back), not a message id. The text is `gs1` and then one line per section, `name:hash:data`, with only digits and `, = / ; @ - .` in the data: `cap` (collection functions this client lacks; a probe with a Classic Era equivalent counts as present when either exists: `GetNumSkillLines`, `GetSkillLineInfo`, `GetMerchantItemInfo`, `GetFactionInfoByID`, and the two `C_AuctionHouse` functions count as present on Era when `QueryAuctionItems`, `GetNumAuctionItems`, `GetAuctionItemInfo`, `GetAuctionItemLink`, `CanSendAuctionQuery`, `PlaceAuctionBid` and `hooksecurefunc` all exist), `level` (`level,xp,xpMax`), `zone` (uiMapID), `money` (copper), `items` (`free;itemID=count,...` for the watch list), `skills` (`skillID=rank/max`, professions only; on Classic Era `GetSkillLineInfo` has no skill ID, so the addon looks the English line name up in `ClaudeWoW.PROFESSION_SKILL_NAMES`, the same table as the bridge's `PROFESSION_SKILL_IDS`; a localized client reports no skills there), `equip` (`slot=itemID`), `factions` (`factionID=reaction/standing`; on Classic Era from `GetFactionInfoByID`, kept only when its 14th return is the asked faction ID), `life` (`deaths,lastDeath`), `recipes` (`recipeID@time`, the last 8 learned), `quests` (`questID@time`, the last 8 turned in, from `QUEST_TURNED_IN`), and, only when the slot field says `obs = 1`, the observed sections from `Observed.lua`: `vendor` (`npcID@time@uiMapID;itemID=price/stack,...`, the last vendor window, at most 40 priced items), `ah` (`itemID=price/quantity@time,...`, the newest of the last 50 auction results that fit in 1,200 bytes (Forever reads at most 12 browse results an event); on Classic Era each quote ends with `/rows/stack`, the auctions behind it and the stack size of the auction that set the price) and `loot` (`<n|o|f><id>_<spellID>@time@uiMapID@x@y@itemID=qty/...` separated by `;`, the last 8 loot samples; x and y in tenths of a percent, empty in an instance). Deaths and recipes are kept per character in `ClaudeWoWDB.telemetry.chars` (20 characters at most), so an alt never replays its main's. A record carries only the sections whose hash differs from what the addon believes the bridge holds, and is at most 1.5 KB.

The transport rules, all test-enforced:

- **Never in the message id space.** `submit()` in `bridge.js` branches on `kind=gs` first, before the shot fallback, the signal report, `alreadyHandled`/`markHandled`, `state.lastId`, `clearSignalsAhead` and any `ack`/`sig` signal, and anything the telemetry code throws is caught and logged there. The bridge keeps its own `handled.gs[session]` set (in memory, 500 per session). It is keyed by session so that two addon lifetimes, two clients or the saved data before and after a wipe, never share one dedupe set. A section is applied only when its sequence is newer than the one in `snapshot.json`. `tests/e2e/telemetry_test.js` sends 300 records whose sequences overlap the message ids and proves no `ack` or `sig` file is spent, `lastId` does not move, and a message sent between them is answered; frames of `[message, gs]` from the real addon and `[gs, message]` each spend exactly the message's one `ack` and one `sig`.
- **Fire and forget.** Records are never in `run.outbound`: no ack wait, no retry, never `pixelFailed`, never `ArmAutoRefresh`. A record counts as sent only when its shot succeeds (a level up, death or new recipe whose shot fails gets one more immediate try, then normal pacing): a shot that fails, times out, or is called off before it fires (its messages were cancelled, or a redraw had no room for it) hands the record's sections back, and they go out with the next one. A lost record is also found through the hashes in the slot files and in `Inbox.lua` at login: a section the bridge holds with another hash is sent again once the bridge has seen a newer record, or after 60 s.
- **Only on the screenshot transport, and only while the bridge is heard from** (`ShotsPaused`, without the Connect override). A record rides on a shot the addon takes anyway for a message, after every message record, in whatever room the frame has left (3,200 bytes); it never pushes a message out, and it never rides on a message's retry, where extra rows could make a short message fail again. A shot of its own happens at most once every 2 minutes, and only after a change event (`PLAYER_MONEY`, `PLAYER_XP_UPDATE`, `ZONE_CHANGED_NEW_AREA`, `BAG_UPDATE_DELAYED`, `PLAYER_EQUIPMENT_CHANGED`, `SKILL_LINES_CHANGED`, `UPDATE_FACTION`), or within a tick (5 s) of a level up, death or new recipe; never while an edit box has the keyboard (`GetCurrentKeyBoardFocus`). At most one record every 30 s (importance-3 events excepted) and 120 an hour.
- **Gated on the bridge.** The addon sends nothing until a slot file, or an `Inbox.lua` written in the last 5 minutes (the Orders card's rule), carries `gs` with `v = 1`; an older bridge would run an unknown record as an empty prompt. `/claude config telemetry off` (or the gear menu's **Send game state, prices and loot to Claude**) and `/claude config context off` stop it. A player message can wait at most `SHOT_TIMEOUT` (3 s) behind a telemetry-only shot the client is already writing: screenshot events carry no id, so the addon never starts a second shot before the first one's event, or its 3 s timeout. Like every message shot, a telemetry-only shot makes the client show its own "screen captured" text: in the `forever` UI source, `Blizzard_ActionStatus` (both its Classic and Mainline files) shows `SCREENSHOT_SUCCESS` on `SCREENSHOT_SUCCEEDED` and fades it out over 2 s, and plays no sound; the addon does not hide it. Not yet checked in the game which of the two files Forever loads.

The bridge writes `goals/<character>/snapshot.json` (each section with its sequence, hash and raw data; a section that does not read back is dropped with a log line, an unreadable file starts fresh) and appends changes to `events.jsonl` (5 MB, then `events.1.jsonl`; 2 files kept). It is the only writer. The slot field lists up to 4 characters, the most recently updated first, each with its session, sequence and hashes. `claude-wow events --follow [--min N]` tails that file for a live session's Monitor, merges 10 s bursts and prints at most 40 bursts an hour; a watched item reaching its target adds a `goal_complete` event (importance 3), once per target: `snapshot.json` remembers it (`completed`), so a count that dips and recovers does not complete again; any record after the watched target changed forgets it, so a new target, or the old one set again, completes again. A snapshot written before `completed` existed may fire one repeat.

Two readers sit on these files. `bridge/goals.js` takes the `equip` section for `gearset` goal progress, through the telemetry's in-memory snapshot of the same character key. `claude-wow report` (`bridge/report.js`) reads `events.jsonl`, `snapshot.json` and `goals.json` to print one day. The Twitch vote collector (`bridge/votes.js`) holds an anonymous, read-only IRC connection only while a vote is open, and sends counts, never voter names, to the stream service.

The observed sections are rings, not events: each holds the latest entries, and the bridge appends to `goals/<character>/observed.jsonl` only the entries it has not written before (it remembers the keys of the last 512 KB of `observed.jsonl` and of `observed.1.jsonl`, so a restart or a new addon session never writes a sample twice). Each line is one observation with `trust: "observed"`, `n: 1` and `at` (epoch ms of the observation); the file rotates at 5 MB to `observed.1.jsonl` (2 files kept). The addon reads only windows the player opened: `MERCHANT_SHOW` (`GetMerchantNumItems`, `GetMerchantItemID`, `C_MerchantFrame.GetItemInfo`, or on Classic Era `GetMerchantItemInfo`, the vendor from `UnitGUID("npc")`), `AUCTION_HOUSE_BROWSE_RESULTS_UPDATED` and `COMMODITY_SEARCH_RESULTS_UPDATED` (`C_AuctionHouse.GetBrowseResults`, `GetCommoditySearchResultInfo`), on Classic Era `AUCTION_ITEM_LIST_UPDATE` (`GetNumAuctionItems`, `GetAuctionItemInfo`, `GetAuctionItemLink`), read once per search sent through the Blizzard browse function: a `hooksecurefunc` on `QueryAuctionItems` counts every query from any addon and keeps its text and exact-match arguments, hooks on `DequoteString` and `AuctionFrameBrowse_Search` (hooked on `ADDON_LOADED`, which is then unregistered) mark the player's own when that call sent exactly one query in the same frame with `CanSendAuctionQuery("list")` true before it, a hook on `PlaceAuctionBid` and `AUCTION_HOUSE_CLOSED` drop it, and the list is read only when no query ran after it, `AuctionFrame` is shown, every unsuffixed row name contains the search text (ASCII case only) and the whole result fits on one page of at most 50; the ring holds 50 quotes and the section sends the newest that fit in 1,200 bytes; a row with no link or item info makes it wait for the refire ([CONFIGURATION.md](CONFIGURATION.md#game-state-telemetry)), and `LOOT_READY`/`LOOT_OPENED` (`GetNumLootItems`, `GetLootSlotType`, `GetLootSlotLink`, `GetLootSlotInfo`, `GetLootSourceInfo`, `IsFishingLoot`, `C_Map.GetPlayerMapPosition`, `UnitIsDead`). One loot window is read once (a second loot event within 2 s or before `LOOT_CLOSED` is ignored) and one source GUID once per spell (the last 64 GUID and spell pairs are remembered), so a corpse opened twice is one sample while its skinning after the kill loot is a second one. The addon remembers the player's last `UNIT_SPELLCAST_SUCCEEDED`, and one cast keys at most one window: when it came within 1 s before the window and is in the slot field's `gather` list, the sample's source carries the list's root spell for that gathering line, so skinning loot is never counted with kill loot and ranking up does not split samples; any other cast keys nothing (spell 0), so a finisher just before autoloot leaves the kill sample alone. A loot window whose source GUID is the current target while `UnitIsDead("target")` is false comes from a living unit, a pick pocket: that source gets no sample and no GUID mark, so the kill loot that follows is still a sample of its own. The bridge builds the list from the synced data of the client's flavor (Forever or Classic Era, [CONFIGURATION.md](CONFIGURATION.md#game-data)): the trainer-learned abilities without reagents or a trivial range of the skill lines named Herbalism, Mining and Skinning and their child lines, from `client-data` rows for the client's build family. It leaves out any spell with a `SpellReagents` row, any ability with a trivial-rank range and any ability learned with the skill line (`AcquireMethod` 1), and every spell whose `SupercedesSpell` chain reaches one of those. Every kept spell maps to one root per gathering line, the lowest kept spell ID of that line. At most 80 spells, cut only after filtering, with a log line when the cap cuts. Build 1.60.1.70094 gives 28 spells and Classic Era 1.15.9.70003 gives 14, both with the roots 2366, 2575 and 8613. These are not yet checked against the synced spell names as the gather casts themselves. The list needs the `skilllines`, `skilllineabilities` and `spellreagents` tables; without them, without synced data or with data for another build family it is empty, the bridge logs why once, and the addon reads no loot at all, since it could not key it. Auction results with an item suffix or a pet species are not recorded, and a result already in the ring with the same price and quantity (and, on Classic Era, the same rows and stack) in the last 5 minutes is not recorded again. Nothing is collected while telemetry is off or the bridge does not ask for it; the rings live in memory only.

`capture.ps1` finds the game window by process name, captures the client area's top-left 800×192 px with GDI (`CopyFromScreen`, DPI-aware), samples the center pixel of each cell, and validates magic, length and checksum. It prints one JSON line per new message and rate-limited warnings when a frame is seen but rejected. `bridge.js` restarts it if it exits. Off Windows, `capture_x11.py` does the same through libX11 (ctypes, no packages): it finds the game's Wine window by its WM_CLASS, grabs the corner from the root window, and searches a few pixels around the origin for the magic so a misaligned window still decodes.

### Open link records (`kind=url`)

A left click on an `http://` or `https://` link in a reply asks the bridge to open it in the PC's default browser. The bridge starts a program on the player's PC because of data the game wrote, so every rule below holds on the bridge side, whatever the addon does:

- **The record.** `session, chat, id, "", "kind=url", "", <url>`: a control record in the message id space, like `kind=dm`. `submit()` in `bridge.js` branches on it after the dedup and before the context, forget, cancel and hello branches: it marks the id handled, hands it to `bridge/openurl.js`, acks it with the result and publishes the slot files at once. No agent runs, and the context is not read off it. The reload outbox has no `kind` field, so a record from there is never one (the opener also refuses `via: 'reload'`).
- **Only plain web links.** At most 2,048 characters, only the characters the addon's link pattern takes (`A-Z a-z 0-9 - . _ ~ : / ? # @ ! $ & ' ( ) + , ; = %`: no whitespace, control characters, quotes, backslash, backtick or non-ASCII), lowercase `http://` or `https://` followed by a letter, digit or `-`, so never a leading `-`. Then the WHATWG `URL` parser: the protocol must be `http:` or `https:`, the host non-empty, and the link must carry no user name or password. The parsed `href` is what is opened.
- **Only links the agent wrote in that chat.** The link must be exactly one of the links in the chat's `links` list in `transcripts.json` (the newest 200). Only an agent run's own result text adds to it: `runJob` keeps the agent's final message (`job.agentText`, before the bridge adds any note) and `finish` hands only that to `noteMessage`. That covers every plugin that runs the agent through `core.runAgent`: `ask`, `claude-code` and `roast`. A reply a plugin writes itself with `core.reply` or `core.late` (`@dev` output, a `live` session's `wow_reply`, stream lines, the factory's late reports), a bridge error and the player's own text never add a link, because each can echo text the game sent. The stored message text is never scanned either, since the 4,000-character cut there can leave a prefix of a link the agent never wrote. A link only in such text, in another chat, a prefix of a listed link, or on a record whose client is not the chat's is refused. Chat ids are letters and digits only: `jobsFromStrip` drops a record with any other chat id (as the reload outbox parser always did), and the transcript lookups on this path read own properties only (`Object.hasOwn`), so a chat id such as `__proto__` or `constructor` never reaches `Object.prototype`. When another client sends with the same chat id, the chat's list is cleared before its reply is noted. Deleting the chat (`d` record) drops its transcript and with it its links. Chats from before this list existed have none: a link there opens once the agent has replied again in that chat.
- **No shell.** `spawn` with an argument list and `shell: false`. The result waits for the child: its `spawn` event is `ok`; its `error` event (a missing `xdg-open`, say) is `refused` with the fixed reason "the browser opener failed to start", and the error goes to `bridge.log`; with neither event in 2 s the link counts as opened and a line says so. The launchers: `/usr/bin/open <url>` on macOS, `xdg-open <url>` on Linux (and FreeBSD/OpenBSD), `%SystemRoot%\System32\rundll32.exe url.dll,FileProtocolHandler <url>` on Windows. Never `cmd /c start`. Other platforms get no launcher and the capability is not offered.
- **Rate limit.** One launch every 2 s and 20 an hour, counted over launches (a launcher that then fails to start still counts); refusals before the launch do not count. Every open and every refusal is one `bridge.log` line, with the input escaped and cut to 120 characters.
- **The result goes back on the ack.** The entry for the record in the slot field `acks` carries `open = "ok"` or `open = "refused"` with `why`, a short reason (at most 80 characters, never the link): `{ session = "...", id = 12, open = "refused", why = "rate limit: 20 links an hour" }`. An ack repeated for a retried strip keeps the result. The addon waits for it: after the ack file fires it reads one slot a second later, and until an ack arrives it reads a slot 4, 12 and 25 s after the click (so a client without working signal files, such as Classic Era, still gets the answer). On `refused` it shows "Link not opened: <why>. Copy it from the box." in `UIErrorsFrame` and opens the copy box with the link. With no answer 40 s after the click it does the same with "no answer from the bridge".
- **Consent.** Only a click sends the record; nothing opens on its own. The addon sends it only for a left click with no Ctrl or Shift, only for a plain web link (the same character and length rules, checked before anything else) that it finds whole in an assistant message of one of its chats (the active chat first), only while the bridge is not down, and only in `pixel` mode (the strip, not the reload outbox). Its gate is wider than the bridge's: one record waiting for its answer at a time ("Still opening the last link" for a click meanwhile) and one every 5 s ("Wait a moment before the next link"). On a sent record it shows "Opening in your browser" in `UIErrorsFrame`. A right, Ctrl or Shift click, or a link it will not send, opens the copy box as before.
- **No retry on any transport.** Once a url record went into a chat log frame that was written, or into a screenshot that fired (`Screenshot()` was called with it on the strip), it is marked sent (`sentOnce`), and `RefreshStrip` leaves it out of every later frame: the 40 s strip retry, the chat log's screenshot retry, the re-send after a transport change, and the frames of other messages sent or retried while it waits. A strip drawn for a shot that has not fired yet still carries it, so a redraw in those two frames (another record acked or added) never drops it. Only a screenshot the client reported as failed (`SCREENSHOT_FAILED`, so no file was written) clears the mark, and the record is shot again within its 40 s. On the deprecated pixel transport the strip is one continuous send, so the record stays on the strip until its ack or its 40 s, like every record there. It leaves the outbox 40 s after the click whatever happened: a late open is worse than none. The bridge drops a second copy of the same id anyway (dedup on `(session, id)`).
- **Capability.** Every slot file and `Inbox.lua` carry `openUrl = true` while the bridge can open links (`openLinks` is not `false` in `config.json` and the platform has a launcher). The addon reads it on every slot read (a later slot without it turns it off) and from `Inbox.lua` only when that file is less than 5 minutes old. Without it the click opens the copy box, so an older bridge never sees the record.
- **Tests.** `tests/openurl_test.js` (the URL table with hostile inputs, the exact-link rule, the launchers, the rate limit), `tests/openurl_addon_test.js` (clicks, the gate, the fallback, the result on the ack, the polls, the 40 s expiry on the strip and on the chat log) (also: every frame decoded record by record, so a url record is in exactly one frame next to other messages and their retries, on the screenshot and the chat log transport, and after a transport change; exact slot reads per click, at most four) and `tests/e2e/openurl_test.js` (the real addon and bridge, with `CLAUDE_WOW_OPEN_LINKS_LOG` set so the bridge writes each launch to that file instead of starting it: an agent link opens, a link only the game holds and a link an `@dev log` reply echoed are refused and come back to the copy box, and chat A's link on a record for chat B opens nothing).

### The screenshot transport

The default (`capture.mode` unset or `"screenshot"`); `"pixel"` turns the deprecated continuous capture back on. The bridge names its transport in every slot file (`transport = "screenshot"`); the addon keeps the last one heard in its saved settings and, from then on, sends differently: `RefreshStrip` draws the strip, waits two frames on the strip's `OnUpdate` so it is really rendered, calls `Screenshot()`, and hides the strip on `SCREENSHOT_SUCCEEDED` / `SCREENSHOT_FAILED` (both exist in the Forever client; a 3 s timer covers a missing event). Each outbound record is shot once (`rec.shot`); the 40 s retry clears the flag, a failed shot is retried at once up to three times, and a hello or forget record is only considered delivered when its ack file arrives (in pixel mode "the bridge was seen after it went up" is enough, because the strip stays up). Before its first switch the addon does not know the transport, so the login hello goes up pixel-style until the hello poll's slot says otherwise. Once the bridge has been silent for as long as `BridgeState` takes to call it down (5 minutes with presence beats, 22 without; `ShotsPaused`), no more shots are taken: the player is told once, the strip goes up pixel-style so the retries and the reload fallback carry the message, and shooting resumes (said once) when the bridge is heard from again; a Connect click buys exactly one shot meanwhile. The bridge sweeps the folder at startup and every 5 minutes (`sweepOrphans` in `bridge/screenshots.js`): client-named files older than a minute whose pixels decode to a strip are deleted, everything else stays. While the mode is on the addon sets `screenshotFormat` to `png` (`tga` if the client refuses) and keeps the player's own value in its saved settings, restored when the mode ends, at `PLAYER_LOGOUT` and, because a crash skips that event, at load (`ADDON_LOADED` and `PLAYER_LOGIN` both run `SyncScreenshotMode`) when the value is still the addon's `png`/`tga`; a stored original is never overwritten with one of those, and a value the player set by hand in between is kept as the new original.

On the bridge side `screenshots.js` watches each client's `<client>/Screenshots` (one watcher per entry in `clients`, see [Several clients](#several-clients); `fs.watch` plus a 1 s scan) for `WoWScrnShot_*.png|tga`; a file counts once its size is unchanged over two checks. `decode.js` reads it (PNG: 8-bit gray/RGB/RGBA/palette, all filters; TGA: raw and RLE, 24/32-bit, either row order - the client writes RLE 32-bit top-left) and applies the same cell, magic, length and checksum rules as the capture scripts, searching a few pixels around the origin. A file holding a strip is deleted after it was read, whatever the verdict; one without a strip is the player's own screenshot and stays. At startup the watcher also takes the client-named files younger than a minute (a strip shot just before the last bridge stopped) and reads them the same way, once; older files are left to the sweep, which uses the same clock, so no file is both read and swept. The bridge publishes its slot files once at startup so the addon's first slot read learns the mode. `Screenshot()` is not protected in the Forever client (it was probed from addon code; `/run` is blocked there, which made earlier probes misleading), and a PNG or TGA screenshot is a bit-exact copy of the frame (grey levels 0, 20, 40, 60, 90, 120, 180, 255 came back exactly; JPEG did not), which is what makes a lossless read possible.

Because of that, the strip need be neither bright nor coarse on this transport. The slot file carries `strip = { on = 60, off = 0, codec = 2 }` (`capture.screenshotLevels`, `capture.screenshotCodec`). Codec 2 is the dense strip: 2×2-pixel cells, each channel at one of four levels spread evenly from `off` to `on` (0/20/40/60 by default, `Codec.DenseLevels`), six bits a cell, 400 cells a row, magic `C7 2A`, and four ramp cells in front holding every channel at level 0, 1, 2, 3. `decode.js` reads the four levels per channel off the ramp and classes every later sample by the nearest (`denseReader`), so the numbers are the drawer's business and a ramp that does not rise in all three channels is not a strip; the byte stream after the magic is codec 1's. Eight times the payload per screen area: a typical message (a few hundred bytes with its record fields) is one 800×2 px near-black line for two frames, and a 1 KB message four rows, 8 px, where codec 1 took fourteen rows, 56 px. With the default levels a bit-exact screenshot puts every sample exactly on a level, so the nearest is never in doubt; the ramp costs four cells and is there so that any four levels a bridge and an addon agree on, or a client that one day curves its screenshots, decode the same. The magic names the codec, so versions never mis-read each other: an addon from before the field ignores `codec`, draws codec 1 at the two levels (`StripCodec`) and this bridge reads it (`findStrip` tries both magics at every offset); a bridge from before it never asks for codec 2, so a current addon draws codec 1 for it; `capture.screenshotCodec: 1` asks for codec 1 outright. The pixel transport keeps codec 1 at full primaries and the `>= 128` threshold in every capture script: a screen capture goes through gamma, scaling and the odd lossy path, where only saturated colours are safe. Not verified in the game yet: that the client renders a 2 px texture on exact pixel boundaries (4 px cells were; the decoder samples each cell's second pixel and searches a few pixels around the origin, and a checksum failure or a strip that is never found is what a misalignment would look like: `capture.screenshotCodec: 1` is the way back).

### The chat log transport (experimental)

Off by default (`capture.chatLog.enabled`). It rides on the screenshot transport: the slot file still says `transport = "screenshot"`, and adds `chatlog = { line = 900, filler = 50000, key = "<32 hex>" }`, so an older addon ignores it and keeps shooting.

- **Out of the game.** The client has a chat log, `Logs/WoWChatLog.txt` (`LoggingChat(true)`), and `SendSystemMessage(text)` puts a local `CHAT_MSG_SYSTEM` line into it. Nothing goes to Blizzard's chat servers. `print` and `AddMessage` lines are not logged.
- **The buffer.** The client holds the log in a write buffer and the file does not change after a few short lines, after `/chatlog` off, or after `/reload`. Measured on 2026-09-30 with `/claude probe chatlog` and `node dev/transport-probe.js`: the client appends each line to a buffer and writes the buffer out when it holds 49,152 bytes (48 KiB) or more. Two writes of 49,297 and 49,204 bytes came in the same second as the probe lines; a 16 KB probe alone wrote nothing, and 31,627 bytes logged earlier that day stayed in memory for 36 minutes, until the character left the world. Lines of 1,000 characters arrive whole, and lines a chat filter hides are still logged. So every frame is followed by `filler` bytes of padding lines (50,000 by default), which guarantees one write after the frame's last line.
- **The frame.** The same byte stream as the strip, `[C7 3A] [id] [len] [payload] [Fletcher-16]`, in base64, cut into lines of `line` characters: `CWX1 <key> <id> <seq>/<total> <chunk>`, then `CWX1 <id> pad zzz…` lines (`Codec.LogLines`). A `CHAT_MSG_SYSTEM` filter hides lines that start with `CWX1 ` from the chat frames (`show = true` in the slot file leaves them visible).
- **Trust.** Other players' chat is logged in the same file, so the bridge reads a frame line only when the `CWX1` tag comes directly after the client's timestamp. Only a local system line has that shape; a whisper, a say, a channel line or an emote has the sender's name or the channel first. A valid frame inside such a line is ignored. That alone would rest on chat text never holding a line break, so every frame line also carries a key: 32 random hex characters the bridge makes once (`state.json`, `chatLogKey`) and hands to the addon in the slot file. The key is in local files only (`state.json`, the slot files, the addon's saved settings and the chat log itself), and with `show = true` the chat frame gets the line with `...` in place of the key. The bridge drops a line with another key or with none, and says so in its log at most once in 5 minutes (`tests/chatlog_test.js`). To change the key, delete `chatLogKey` from `state.json` and restart the bridge. A watcher that starts in the middle of a line drops the rest of that line.
- **Into the bridge.** `bridge/chatlog.js` polls the file size every 250 ms from the end of the file as it was at startup, keeps a partial last line for the next read, collects the chunks of a frame, checks magic, length and checksum, and hands the payload to the same `jobsFromStrip` and `submit` as a decoded strip (`via: 'chatlog'`). A file that shrinks is read again from the start; dedup on `(session, id)` drops repeats.
- **Fallbacks.** `RefreshStrip` uses the chat log only for the first try of a frame with no vision record, while the bridge is not dark. A logged record with no ack after 8 s (`ChatLog.RETRY_SECONDS`; 15 s when the signal files are not proven to work in this game process, as on Classic Era, where acks come from slot polls) goes out again by screenshot, and the usual retries and the reload fallback follow. A hello, forget or cancel has no reply to carry its ack, so on such a client it read the ack only from the signal file and always went out again by screenshot. The bridge now lists the records it acknowledged in the last 10 minutes in every slot file (`acks`), and the addon marks them acknowledged on any slot read; a forget or cancel sent on the chat log arms one slot poll 4 s later when the signal files are not proven (the hello has its own poll at 5 s). An ack that only came after the screenshot retry is a miss. Two misses in a row pause the chat log for 10 minutes; then one message is a trial. A late trial doubles the pause (up to 1 hour), an ack on the first try ends it, and new padding from the bridge ends it at once.
- **Calibration.** The bridge keeps the sizes of its last 30 reads of new bytes from the file (`state.json`, `chatLogWrites`). A read is one client write, or several when they land inside one 250 ms poll. The most common group of three or more sizes within 2 KB of each other is taken as the client's buffer size. When a group at half that size has at least half as many reads, the half is taken instead, because the larger one is then two writes in one read. The padding in the slot file is that size rounded up to 1,000, and never less than the configured `filler`, so a few small writes at logout cannot lower it. A buffer past 65,536 bytes takes `chatlog` out of the slot file, and messages go by screenshot. A client without `SendSystemMessage` or `LoggingChat` never uses it. `/claude diag` shows the state and the counts.
- **Cleaning.** The client keeps its own write position in the file: after a truncate it wrote at the old position and left a gap of zero bytes (measured 2026-10-01). So the bridge never changes the file while the game runs. At startup and every 5 minutes, when no process runs from the client's folder and the file has been still for a minute, it removes the `CWX1` lines in place and keeps every other line (`cleanWhenClosed`; `capture.chatLog.clean: false` turns it off). `bridge/clientproc.js` decides whether the game runs, and only a clear "no" lets the clean go ahead:
  - macOS: `ps -axo command=`; a command line that holds `<folder>/` is the game.
  - Windows: PowerShell `Get-CimInstance Win32_Process`, each name and `ExecutablePath` sent back as base64 UTF-8 between start and end lines, 20 s timeout. A path inside the folder (no case, `/` or `\`, `\\?\` stripped, a separator after the folder so `_classic_era_` never matches `_classic_era_2`) is the game. A process whose name starts with `Wow` and whose path Windows hides means "cannot tell".
  - Linux: first the environment. In WSL (`/proc/sys/kernel/osrelease` holds `microsoft` or `WSL`), in a container (`/.dockerenv` or `/run/.containerenv` exists), or with the client folder under `/mnt/<letter>/`, the game can run where this `/proc` cannot see it, so the answer is "cannot tell". Then every `/proc/<pid>`. For the bridge's own user, the game runs when the `exe` link, the `cwd` link or a Unix path in `cmdline` is inside the folder, or, for Wine and Proton (`wine64-preloader`), a `C:\...` path in `cmdline` whose folder part, with the drive letter dropped, matches the end of the client folder (case does not count). Any other `Wow*.exe` argument, with or without a folder, means "cannot tell". For another user, and for an own process whose `exe` or `cwd` link gives `EACCES` or `EPERM` (one that is not dumpable, such as `ssh-agent`), only the world-readable `cmdline` is read: one that names a `Wow*.exe` or the folder means "cannot tell". Any read error except a process that ended during the scan means "cannot tell".
  - The folder is matched as configured and as `realpath` resolves it. A failed command, a timeout, an empty list or a line that does not parse means "cannot tell", and the file is not touched. Any other platform logs a warning at start and never cleans. The check is asynchronous (`execFile` with a timeout, `fs.promises` for `/proc`), so a slow PowerShell never blocks the bridge. A file that changed while the check ran is not touched, and a "closed" answer more than 3 s old when the file would be shortened is not trusted: the file keeps its length. Each "cannot tell" reason is logged once (at most 16 reasons). Two checks never run at once: a tick that comes while one runs is skipped. A failed clean never stops the 5-minute timer.
- **Game state.** A `kind=gs` record rides on a message's chat log frame in the room the messages leave, as on a screenshot. An idle record goes out as a chat log frame of its own with id 0, under the same gates as the telemetry-only shot it replaces (at most one every 2 minutes, never while an edit box has the keyboard, none while the bridge is dark). It counts as delivered when the write succeeds; a bridge that did not keep it shows that in the `gs` hashes, and the addon sends it again. While the chat log is paused or off, the telemetry-only screenshot comes back.
- **Costs.** Chat logging stays on for the session, so the player's chat goes to `WoWChatLog.txt` as with `/chatlog`. Each send, and each idle game state frame, adds the frame plus about 50 KB of padding to that file until the game closes and the bridge cleans it: with game state changing all the time, at most about 1.5 MB an hour.

**Vision** rides on this transport for free: the file the client wrote is the whole screen, and the strip is only its top-left corner. When a record carries the `v` flag (`/claude config vision on`, or `/claude look` for one message), `handleScreenshot` hands the decoded image to `vision.js` before deleting the file: `gameView` drops the rows the strip covered (`decodeStrip` reports them) and box-filters the rest down to `vision.maxWidth` (1280) pixels wide, `encodePNG` writes a Paeth-filtered RGB PNG (1.5-2 MB for a 1080p frame), and one copy per asking message goes to `~/.claude-wow/tmp/vision-<id>-<time>.png`, never more than `vision.keep` at once (all swept at startup). `runJob` reads it back when the run starts, opens the message with a paragraph saying an image of the player's screen is attached (only then; never the system prompt, which is recorded once per chat and cached), and hands it to the agent: Claude as an Anthropic `image` content block in a stream-json user message (`--input-format stream-json`; no tool call involved), Codex with `-i`, Hermes with `--image`, Grok as a path in the prompt. The file is deleted when the run ends. The pixel transport has no full frame, so there the flag is logged and ignored.

`capture_mac.py` (macOS, native client) does the same on the window's top-left corner, found through System Events, and searches a taller area for the magic since the title bar pushes the UI down. It captures only the strip plus its search margins (808x272 points by default) with CoreGraphics called in-process through ctypes (`CGWindowListCreateImage`, ~20 ms a frame, no child process, no PNG); when that cannot load, or Screen Recording is not granted, it falls back to the `screencapture` binary writing a raw BMP per frame (~125 ms), which is where the permission errors get their names. `--backend screencapture` or `CLAUDE_WOW_MAC_BACKEND=screencapture` forces the fallback. Exclusive fullscreen blocks GDI capture; borderless/windowed works. HDR was not tested. On Linux, Wayland sessions block reading other windows, and a compositor that unredirects the game window can hand back a black or stale frame (`capture.keepComposited` asks it not to).

## Inbound: load-on-demand slots

`install-slots.js` creates `ClaudeWoW_S001` … `ClaudeWoW_S200`, each a `## LoadOnDemand: 1` addon with a single `Inbox.lua`. `C_AddOns.LoadAddOn` reads that file from disk at load time; each slot can be loaded once per UI session, and `/reload` unloads them all.

The bridge doesn't know which slot the game will load next, so every publish writes the same content to all 200 (atomic rename per file, ~1 MB total, cheap). The content is the latest status of every chat:

```lua
ClaudeWoW_SlotData = {
  ts = "...", now = <bridge epoch seconds>, cwd = "<the bridge's default folder>",
  agent = "claude", agents = { "claude", "codex", "grok", "agy", "hermes" },   -- the default agent, and the ones the bridge knows
  efforts = { ["ask"] = { ["claude"] = "medium", ["codex"] = "" }, ... },   -- per plugin, the --effort the bridge passes each agent that takes one ("" = it passes none, so the agent's own settings or model decide); an agent left out has no effort option. Old addons ignore it
  effortLock = { ["claude"] = "high" },   -- CLAUDE_CODE_EFFORT_LEVEL in the bridge's environment, which every Claude run inherits and which overrides --effort
  openUrl = true,   -- the bridge opens reply links in the browser (kind=url records); left out when openLinks is false or the platform has no launcher
  transport = "screenshot",   -- the addon must call Screenshot() with the strip up; or "pixel" (deprecated): the bridge screen-captures it
  strip = { on = 60, off = 0 },   -- screenshot transport only: the levels to draw the strip at
  transportNote = "pixel transport, fallen back to since ...",   -- only when the bridge fell back to pixels on its own; /claude diag shows it
  addonDisk = { version = "0.4.0", build = "1a2b3c4d5e6f" },   -- the installed ClaudeWoW.toc: Version and X-Build (Reload or restart notice)
  bridge = { version = "0.4.0", protoMin = 1, protoMax = 1 },   -- the bridge's semver and the addon protocols it accepts (Version handshake); left out only by bridges older than the handshake
  acks = { { session = "<addon session>", id = 12 }, { session = "<addon session>", id = 13, open = "refused", why = "..." }, … },   -- records acknowledged in the last 10 minutes, at most 24: the ack path for a client whose signal files do not work; a kind=url record's entry carries the open result
  replies = { { chat = "...", id = 12, status = "working"|"done"|"error", text = "...", cwd = "...", session = "<agent session id>", agent = "codex", denied = { "WebSearch" }, macros = { { name = "Charge", body = "#showtooltip\n/cast Charge", icon = nil, char = false, risky = false } } }, … },
  map = { epoch = "...", version = 3, layers = { … } },  -- the agent's map layers (docs/MAP.md): for a while after they change and after every hello
  widgets = { epoch = "...", version = 2, items = { { name = "dps", title = "...", rev = "<sha1>", source = "<lua>" } } },  -- live UI widgets (docs/UI-WIDGETS.md), shared like the map
  goals = { rev = 12, char = "Bone-ClassicBetaPvP2", order = { id = "o_12", text = "Skin 30 more", pct = 83 }, goals = { { title = "Cooking 75", pct = 14 } } },  -- the Orders card (docs/LIVE-SESSION.md): no order = hide the card; at most 3 goals and 640 bytes. Left out only when the context names no character, and by bridges older than the card
  dm = { rev = 4, char = "Bone-ClassicBetaPvP2", now = <bridge epoch seconds>, manual = true, beat = { id = "b2", title = "...", lines = { "...", … } } },  -- the DM frame (docs/LIVE-SESSION.md): no beat = hide it; manual = the next beat waits for /dm next; at most 1,600 bytes. Always sent by bridges that have it, so it is also the capability for kind=dm records
  gs = { v = 1, watch = { items = { … }, factions = { … } }, chars = { { character = "Name-Realm", session = "<addon session>", seq = 1790000000, hashes = { money = "0a1b2c3d", … } }, … }, refused = { … }, obs = 1, gather = { [8617] = 8613, … } },  -- game state records: the capability, what to count, what the bridge holds per character; obs = 1 asks for the observed sections, gather maps each listed spell to its gathering line's root spell (empty: no loot is read)
  restore = { token = "...", chats = { … } },   -- only right after a saved-data reset
}
```

The addon loads a fresh slot on a schedule after each send (5, 10, 16, 24, 34, 46, 60, 80, 100, 130, 160, 200, 240, 300 s, then every 60 s) or immediately when the readiness signal fires. A slot poll matches replies by `(chat, id)` against each chat's pending message. `now` lets the addon know when the bridge last wrote anything (the two clocks are the same machine). A slot file carries the newest 30 reply records per client; a new record moves its chat to the end of that list. Every slot file and `Inbox.lua` also carry `runLimit` (the bridge's `timeoutMs` in seconds) and `alive` (`{ session, id, since }` for each message the bridge runs, queues or holds; `since` is the run's start in epoch seconds, 0 before it starts). The addon frees a pending chat after `runLimit` plus 5 minutes (35 minutes without the field) with no ack, heartbeat, new progress line or `alive` entry for its message, saves that clock on the chat (`lifeAt`) so a reload keeps it, gives a chat left pending by an earlier game session 2 minutes after a real login (`graceUntil`, set only when `PLAYER_ENTERING_WORLD` says `isInitialLogin`), says so once in the chat, reads a slot when the bridge fires that message's sig file (or on the idle poll without signals), and still takes that message's reply if it comes later (`gaveUp` on the chat). A late reply (`late = true`, an answer that comes after its message ended) has a record of its own per answer, keyed `<addon session>:<chat>#late#<lateSeq>` in the bridge; the bridge keeps the last 4 per chat, and the addon shows each `lateSeq` once (the last 8 per chat in `lateShown`). A record with `lateOk` (a live-session stall, or a relayed permission prompt with `lateIn`, the seconds until its timeout) makes the addon poll slots for the late answer at 10 s to 300 s after `lateIn`.

The same content is written to `ClaudeWoW_Runtime/Inbox.lua`, which the game reads on `/reload` — the fallback path and the only path in `mode reload`.

### Version handshake

Two numbers describe each side. The **semver** is `package.json` `version`, also `## Version` in `ClaudeWoW.toc` (`tests/version_test.js` checks they match), and `version` in `assets/plugins/claude-wow/.claude-plugin/plugin.json` (`tests/plugin_test.js`). **PROTO** is an integer for the wire protocol between addon and bridge; it changes only when a change breaks the other side. The bridge has `PROTO` in `bridge/protocol.js` and accepts `PROTO_MIN` to `PROTO_MAX`; the addon has `ClaudeWoW.Version.PROTO`. `tests/version_test.js` checks the two are equal and that the addon's fallback `ClaudeWoW.Version.SEMVER` equals the toc.

- **Addon to bridge.** Every hello carries `ver=<semver>;proto=<n>`. The addon reads its semver with `C_AddOns.GetAddOnMetadata("ClaudeWoW", "Version")` (in both the Classic Era and the Forever binary) and falls back to the constant. A bridge older than the handshake ignores both tokens: `parseFlags` drops unknown tokens, and a hello returns before `runJob`. A hello without the tokens comes from an addon older than the handshake; the bridge counts it as protocol 1 with an unknown semver. The reload outbox carries the same two tokens in its `opts` field, so a session in `mode reload`, which never says hello, is judged by its first message.
- **Bridge to addon.** Every slot file and `Inbox.lua` carry `bridge = { version, protoMin, protoMax }`. The addon reads it in `TryLoadSlot` and in the `Inbox.lua` path, and skips it when the file's `now` is more than 5 minutes old. A file without the field (an older bridge) changes nothing and the addon says nothing. The field needs no slot load of its own: the hello poll reads it.
- **Verdicts.** Protocol outside `[protoMin, protoMax]`: the bridge answers every message from that session with an error reply that names the side to update and how, and runs no agent; the addon says the same in the chat once per UI session. The check is in `runJob`, so a queued message is judged when it starts. It reads the session's last hello in `state.json`: a session with no hello on record (a wiped `state.json`) is not refused until it says hello again. Only the semver differs: one line, once per UI session, that names the older side; nothing is refused. Equal: nothing is said. Both sides build the same words (`P.versionVerdict`, `ClaudeWoW.Version.Verdict`).
- **Where it shows.** The bridge keeps the last hello of up to 8 sessions as `addons` in `state.json` and logs a changed verdict. `/claude diag` shows a `versions:` line, `claude-wow service status` a `versions` line (with the version of the installed bridge), and `npm run doctor` a **Versions** check that fails on a protocol mismatch.

### Reload or restart notice

On Classic Era 1.15.9, `/reload` re-reads the toc and every Lua file it lists: a changed file, a file that was missing at launch, a file newly added to the toc, and a new `## Version` (measured with a throwaway addon, 2026-10-02). Only a new addon folder needs a full restart, because the client builds its addon list at launch. Textures and sounds made after launch are not measured, and Forever is not measured.

- `setup` writes `## X-Build: <build>` after the `## Version` line of the toc it installs. The build is the first 12 hex digits of a SHA-256 over every shipped file but the toc, by name and content (`P.addonBuild`). A CurseForge install has no `X-Build` line, so only the version counts there.
- The addon keeps what it loaded, `ClaudeWoW.Version.LOADED = { version, build }`, read from `GetAddOnMetadata` when `ClaudeWoW.lua` runs.
- The bridge reads the installed toc (cached on mtime, size and inode) and puts it in every slot file and `Inbox.lua`: `addonDisk = { version = "0.4.0", build = "1a2b3c4d5e6f" }`. It leaves the field out when the toc has no valid version.
- When the field differs from what the addon loaded, the addon says once per UI session: "New addon files are installed (...). Type /reload to load them." A field written before this addon load is skipped, because a `/reload` right after an install can read an `Inbox.lua` or slot that still names the old build; the hello makes the bridge publish again at once. A malformed field and a client that gives no metadata are skipped too.
- When `C_AddOns.GetAddOnInfo("ClaudeWoW_Runtime")` says `MISSING`, the runtime folder came after launch, and the addon asks once for a full restart. Not measured: that the client reports `MISSING` for a folder made after launch (it does for a slot folder through `LoadAddOn`). If it does not, the notice stays silent.
- `/claude diag` shows `addon files loaded: <version build>, on disk: <version build>`.

## What ships and what the bridge writes

`ClaudeWoW/` holds only shipped files; an addon update (CurseForge replaces the whole folder) may overwrite or delete anything in it. Everything the bridge writes while it runs lives in `ClaudeWoW_Runtime/` (the name is `P.RUNTIME_ADDON` in `bridge/protocol.js` and `Presence.ROOT` in the addon), plus the 200 slot folders:

| Folder | Written by | Holds |
|---|---|---|
| `ClaudeWoW/` | setup (copy of `addon/ClaudeWoW`) | the addon; `Inbox.lua` there is a placeholder, `ClaudeWoW_Inbox = ClaudeWoW_Inbox or { … }` |
| `ClaudeWoW_Runtime/` | setup, `npm run slots`, the bridge | `ClaudeWoW_Runtime.toc` (`## Dependencies: ClaudeWoW`, not load-on-demand, so it loads after the addon), `Inbox.lua` (the reload path), and the signal folders `ack/`, `sig/`, `act/`, `ctl/`, `presence/` |
| `ClaudeWoW_S001` … `ClaudeWoW_S200` | `npm run slots`, the bridge | one slot `Inbox.lua` each (above) |

The addon reads `ClaudeWoW_Inbox` at `PLAYER_LOGIN`, after every addon loaded, so only the order of the two `Inbox.lua` files matters: the bridge's loads last and wins, and the placeholder keeps whatever already loaded. An `inboxFile` in `config.json` that names `ClaudeWoW/Inbox.lua` is read as the runtime one.

Installs from before this layout kept the signal folders in `ClaudeWoW/`. `install-slots.js` (and setup, which runs it) builds `ClaudeWoW_Runtime/` from the presence ring in `state.json`, then removes the old folders and says to restart the game once. A bridge started on such an install builds `ClaudeWoW_Runtime/` the same way and logs it once (`migrate: created …`), but leaves the old folders: deleting them under a running game would read as every signal firing at once. At login the addon probes `ClaudeWoW_Runtime\ctl\valid.wav`; when it does not read valid and `ClaudeWoW\ctl\valid.wav` does (an older bridge, or no restart since the move), it uses the old folders for the session. `/claude diag` names the folder in use (`files: …`), and `npm run doctor` warns about old folders left in `ClaudeWoW/`.

### Several clients

One bridge serves every client in `config.clients` (`bridge/clients.js`): for example WoW Forever in `_classic_beta_` and Classic Era in `_classic_era_`, with one of them or both running.

- **Writes:** every publish writes each client's `Inbox.lua` and its 200 slot files. A client's files carry only the replies to its own messages (`clients.recordsFor`), its own presence ring, its own recent acks, its own chat log padding, its installed addon build (`addonDisk`), and a restore bundle only when the new session token is its own. Widgets, goals, the campaign, `gs` and the project list (`projects`, `home`; `bridge/projects.js`) are the same for every client. Map layers are kept per character in `state.maps`, keyed by the character key of the game context (`maphold.mapOf`; `""` when the context names no character). Each client's slot files carry the map of that client's own character. A run's map commands go to the character its message came from (`job.char`, taken when the message arrives), and `route_draw` goes to the character the game last reported. The addon applies a map only when its `char` is its own character key or is missing (game context off), and keeps the layers in the per-character `ClaudeWoWMapDB`. A general chat's transcript records the first character that wrote in it (`char`), and a restore offers it only to that character. A restore is offered once per session token and character (`transcripts.tokens["<token>#<char>"]`) and names its character (`restore.char`); the addon imports only its own character's bundle and keeps `restored` per character. The addon names its character on every hello and reload-mode message (`char=<hex key>`), which the bridge keeps per client (`clients[key].char`), so maps and restores follow the character with the game context off too. A client that is not running still gets fresh slot files, so its first slot read after launch is not stale.
- **Reads:** one Screenshots watcher, one chat log watcher and one SavedVariables poll per client. Each client also gets its own chat log clean: its own process check against its own folder, its own 5-minute timer that skips a tick while its check runs, and its own once-per-reason log. A record carries no client field: the bridge tags it with the client whose folder it read the record from. The deprecated pixel capture watches the first client only.
- **Signals:** a message's ack, sig and act files, and the 50 slots armed ahead of it, are in its own client's `ClaudeWoW_Runtime` only. Message ids are per client (each addon counts its own), so a slot number means nothing across clients.
- **Presence:** each client has its own ring position in `state.json` (`clients.<dir>.presence`). The bridge beats every client whose runtime folder exists, the same as it beat a closed game before.
- **Context:** each client's last game context is kept next to its ring (`clients.<dir>.context`). A run uses its own client's context for the prompt and for the game data flavor; `state.context` stays the last context of any client for goals and campaigns.
- **Which client is live:** the bridge notes when it last heard each client (`clients.<dir>.heard`) and does not poll the process list. The slot field `clients = { { name, version, build, heard, here, last }, ... }` lets `/claude diag` show every client, its installed build, which one is this client and which one spoke last. A missing field means an older bridge.
- **Transcripts:** each chat records the client that last used it. A restore offers only that client's chats and chats from before clients were recorded.

## Signals: armed files, deleted to signal

`PlaySoundFile(path)` returns whether the file will play. On the Forever client (1.60.1, macOS) a missing file returns `nil`, and an empty, garbage, truncated or valid file all return `true`, so content cannot carry a signal; only existence can. And existence has a second rule: the client only sees files that existed when it launched (fact 2 above). A file created mid-session reads as missing for the rest of the process.

Measured on 2026-09-29, before this scheme: the bridge created `presence/NNNN.wav` every 30 s (the files reached 1981 on disk), the game had launched at about file 1962-1965, and `/claude diag` said `presence: head at 1965, beats seen: 0` and `sound checks: 469, valid hits: 9`. No file created after launch was ever seen, so the light went red 5 minutes after every reply. Every ack, readiness signal and heartbeat the bridge created mid-session was invisible the same way; the addon only got replies from its scheduled slot polls. The headless client now models this (`dev/wow/client.js` snapshots the AddOns tree at launch), and `tests/e2e/presence_test.js` reproduces the old behaviour: 20 presence files created after launch, 0 seen.

So every signal is a file that exists before the game starts ("armed"), and "on" is the bridge **deleting** it (present -> missing). Nothing is ever created mid-session for the game to see.

All paths are under `Interface/AddOns/ClaudeWoW_Runtime/`.

| Files | Armed by | Deleted (fired) when |
|---|---|---|
| `sig/NNN.wav` | setup; the bridge for the 50 slots ahead of each message and when a run starts | reply NNN is ready -> load a slot now instead of waiting for the schedule |
| `ack/NNN.wav` | setup; the 50 slots ahead of each message | the bridge received message NNN -> take it off the strip |
| `act/NNN/kk.wav` | setup; the 50 slots ahead, and when a run starts | the agent's k-th action on message NNN -> live "14 actions, last 6 s ago" |
| `presence/a/kkkk.wav`, `presence/b/kkkk.wav` | setup, then the bridge (below) | one every 30 s, and one at every hello -> the status light |
| `ctl/valid.wav` | setup, never deleted | never; at login the addon checks that it reads as playable and that `ctl/absent.wav` (never created) does not, and disables the whole mechanism if not |
| `ctl/probe-<token>.wav` | the bridge, when a hello asks for it | never; a diagnostic, see below |

`NNN = ((id − 1) mod 200) + 1` (`bridge/signals.js` has the paths). A slot's files can fire once per game process: re-arming one mid-session is a file created after launch, which the game may not see. So before it sends, the addon checks that the message's `ack`, `sig` and `act/01` still read as present; one that is already missing is "spent" and is not trusted for that message (it falls back to the slot schedule). The bridge re-arms the 50 slots ahead of every message, so after a restart of the game every slot it will use next is armed.

**Presence rings.** The bridge keeps two rings of `presenceMax` (2000) files. It beats on one (`state.presence = { ring, at }`: files `1..at` deleted, the rest armed) and keeps the other fully armed. When the current ring is spent (2000 beats, about 16.7 hours) it switches to the other one and arms the spent ring again for the next game launch. A game process therefore always has the rest of the current ring plus a full second ring, at least 2000 beats, whenever it started. The addon finds each ring's head at login with a binary search ("first file that reads present"; the missing prefix is what the bridge already deleted), then probes each head every tick: a head that reads missing is a beat. `bridge.js` never re-creates the current ring's deleted files while it runs; `preparePresence` at startup only arms what is ahead. Each slot file names the ring and position: `signals = "armed"`, `presence = { ring = "a", at = 37, n = 2000, probe = "..." }`. The bridge republishes the slot files with a beat when nothing else published for 30 s, so any slot read carries a fresh clock and position.

**The self-test.** Whether a launch-time file that the bridge deletes then reads as missing was not measured when this scheme was written, and a client could cache a file it already played. So presence only drives the light once the addon has seen it work in this process:

- *pending*: after login, until decided. The light uses the no-presence windows (below).
- *passed*: a head the addon had probed as present read missing after the bridge deleted it. The bridge beats at every hello, so this is decided within one beat of connecting.
- *failed*: a slot said the bridge's position is at or past a head that still reads present. The addon stays on the no-presence windows for the session.

A passed session can still lose presence: a ring the bridge armed after this game started, or a bridge that is up (a fresh slot clock) while no beat arrived for 150 s, marks that ring stale for the session. While presence works and no beat arrives for 150 s the addon spends one slot (at most every 10 minutes) to check.

The result rides on every strip record after it is decided (`pt=passed` or `pt=failed`). The hello also asks for a diagnostic (`probe=<token>`): the bridge creates `ctl/probe-<token>.wav` mid-session, and the addon probes it once, after a slot says it exists, and reports `lc=seen` or `lc=unseen`. `unseen` confirms the launch-time index; `seen` would mean a file is visible when it is never probed before it exists. The bridge logs both (`signal self-test from the game: ...`) and keeps them in `state.json` as `presenceTest`; `npm run doctor` shows them. `/claude diag` shows the scheme, the ring the bridge is on, both heads, the beats seen and the two results.

**Timing.** With beats the bridge is heard from every 30 s, so 90 s of silence is "stale" and 5 minutes is "down". Without them (self-test pending or failed, sound channel off, no ring left) the only evidence is a slot read, and while idle the addon spends one slot every 10 minutes, so the windows are 12 and 22 minutes. With the sound channel off the addon still works: replies come from the scheduled slot polls.

## Bridge

`bridge.js` (its only runtime dependencies are the Chat SDK packages `chat`, `@chat-adapter/discord` and `@chat-adapter/state-memory`, loaded only when `discord.enabled` is on; `chathub.js`), with the pure protocol code in `protocol.js` (strip records, slot files, folders, dedup; unit-tested in `tests/bridge_test.js`), the plugin registry and routing in `plugins.js` (unit-tested in `tests/plugins_test.js`), one module per plugin under `plugins/`, and the agents in `agents.js` (one entry per CLI: the command line for a run, how the prompt is handed over, and a parser that turns its output stream into progress lines, a session id and the reply; unit-tested in `tests/agents_test.js` against each CLI's documented stream format):

- **Inputs:** capture lines; the SavedVariables outbox (fallback, written on `/reload`); `--inject` for tests. Each input belongs to one client folder, and every record it yields carries that client ([Several clients](#several-clients)).
- **Dedup:** `state.handled[session]` is a set of ids; older single-number state is migrated. Game state records (`kind=gs`) never reach it; see [Game state records](#game-state-records-kindgs).
- **Plugins:** the core (this file) owns the transport, chats, sessions, transcripts, restore, the game context, map layers and macros; what a message *does* belongs to a plugin ([PLATFORM.md](PLATFORM.md)). Each plugin declares `id`, `label`, `aliases`, `match(job)`, `tools` (its own instructions, placed in the system prompt right after the reply rules), `surfaces` (`map`: its runs get `CLAUDE_WOW_MAP_FILE` and their map commands are applied; `macro`: macro blocks in its replies become buttons) and `handle(job, core)`. Routing (`plugins.route`): an address at the start of the text (`@ask …`, `/claude …`, stripped from the prompt), else the chat's binding (a `plugin=` flag on the record and `plugin` in the reload outbox; `--plugin` for `--inject`), else the first plugin whose `match()` says yes, else the default (`plugins.default` in the config, else the first registered). An unknown binding gets an error reply listing the plugins. `core` lends a plugin `runAgent(job, { cwd, freshSession, gameData, runTools })` (`gameData`: a Claude run gets the read-only `wowdata` MCP server, [CONFIGURATION.md](CONFIGURATION.md#the-wowdata-server); `runTools`: a Claude run gets the `wowgoals` MCP server for that run only, with a fresh run grant that the bridge revokes when the run ends; the server calls back over the live socket and the bridge stays the only writer, [LIVE-SESSION.md](LIVE-SESSION.md#goals-orders-and-campaigns-from-in-game-chats)), `fail(job, text)`, the bridge's folder, and the folder its session was made in; `state.json` remembers the plugin of each session and a chat that changed plugin starts a new session. Every slot file names the default plugin and the list; a reply record names the plugin that answered, and a restore bundle names each chat's (a transcript from before plugins is a `claude-code` chat). Two ship: `ask` (`plugins/ask.js`, the default), general in-game chat, which runs the chat's agent in a scratch folder of its own (`plugins.ask.cwd`, else the per-user application data folder: `~/Library/Application Support/claude-wow/ask`, `%LOCALAPPDATA%\claude-wow\ask`, `~/.local/share/claude-wow/ask`) with a few lines in the prompt saying it is the player's assistant and not a coding session, and with `gameData` and `runTools` on; and `claude-code` (`plugins/claude-code.js`), what the bridge did before plugins existed: a chat is an agent session in a folder. A fourth, `dev` (`plugins/dev.js`), runs no agent either: it answers `@dev <command>` with the output of one fixed command in the chat's folder (git, `bridge.log`, the test command, `dev/doctor.js`, the game's `Logs/General.log`) and keeps feedback in `feedback.jsonl`. It is `sessionless`: `runJob` adopts no `resume=` session for it, and the addon keeps `resume=`, `live=` and the reset flag off its records and leaves the chat's session alone when a reply names `dev`. It claims the chat's `running` entry (`core.claimRun`) and hands each child to the core (`core.runChild`), so `/claude cancel` and a shutdown end its commands, and `finish()` drops a `running` entry only when it belongs to the finishing job. Its output becomes a one-shot note that `runAgent` puts in front of the chat's next message (`core.setDevNote`). A third, `live` (`plugins/live.js`), runs no agent at all: it forwards the message over a local socket to `bridge/channel.js`, an MCP channel server that a running Claude Code session spawned, and publishes the session's `wow_reply` through `core.reply`; a plugin may declare `start(core)`/`stop()` for such long-lived resources, and `status()` for the `live` field of the slot files ([LIVE-SESSION.md](LIVE-SESSION.md)). On the addon side a chat carries `plugin` (`""` = the bridge's default, sent as no flag at all); chats from before plugins are bound to `claude-code` once, when the addon first runs with the field (`settings.pluginsV1`), and a new chat inherits the binding of the chat it was made from, like the folder and the agent.
- **Folders (the `claude-code` plugin):** the bridge's folder is `--project`, else the folder the bridge was started from (the `claude-wow` command, see README), else `defaultCwd` in the config; it is reported to the addon as `cwd` in every slot file. A chat's folder is resolved against it (`realms` → `<default>\realms`; empty = the default) and must exist. The agents keep sessions per project folder, so `state.json` remembers the folder each session ran in and a chat that changed folder starts a new session. A Claude chat whose system prompt rules changed (`sessionRules`) starts a new session too, except a chat in a `plugins.claude-code.threads` folder: it keeps its session (`runAgent(job, { thread: true })`), and its factory dispatcher rules go first in each turn's prompt (`turnRules`) instead of the system prompt. A kept thread session keeps the system prompt of its first turn: a later game-context change or a release that edits the rules does not reach it until `/claude reset`.
- **Agents:** `agent` in the config is the default; a record's `agent=` flag overrides it for that chat. Unknown names get an error reply listing the known ones; an agent whose CLI isn't installed gets one saying so (`agents.resolveCommand` looks in the installer's folder, on the `PATH`, and behind npm's `.cmd` launchers, which it unwraps to the script or native binary they run rather than going through `cmd.exe`). `state.json` remembers the agent of each session next to its folder, and a chat that changed agent starts a new session. Every slot file names the default agent and the list, so the addon can validate `/claude -c --agent` and label the bubbles; every reply record names the agent that wrote it. See [AGENTS.md](AGENTS.md) for what each CLI is run with.
- **Jobs:** one agent process per chat, up to `maxParallel` at once, queued per chat beyond that. Claude: `claude -p --output-format stream-json --verbose --permission-mode … --allowedTools … [--resume <id>]`, prompt on stdin; Codex: `codex exec --json -C <folder> --sandbox … [resume <id>] -`, prompt on stdin; Grok: `grok --output-format streaming-json --cwd <folder> --prompt-file … [-r <id>]`; Antigravity: `agy -p=<prompt> --output-format stream-json --add-dir <folder> [--conversation <id>]`, prompt on the command line; Hermes: `hermes chat --query-file - --in <folder> [--resume <id>]`, prompt on stdin, plain-text reply read when the process ends. The agent's parser turns its events into progress lines (`edit player.gd`, `$ npm test`) and heartbeat files; its final message becomes the reply. Session ids are stored per chat id in `state.json`, so resuming survives an addon data reset. A run that outlives `timeoutMs` is killed with its whole process tree: on POSIX every child the bridge starts (an agent run, the capture script) leads its own process group (`detached: true` in `procs.js`, which is `setsid` and nothing else: the stdio pipes are wired as before and the bridge still waits for the child), so the kill is `SIGTERM` to the group, then `SIGKILL` to the group after `killGraceMs` (5 s) if anything in it is still there; a child that ignores `SIGTERM`, or a grandchild that keeps the stdout pipe open after the child exited, can no longer leave the chat in `running` and one of `maxParallel` gone until a restart. Windows uses `taskkill /T /F`. The bridge's own `SIGINT`/`SIGTERM` handler ends every child the same way and waits for their `close` (so each run's error is published to the chat) before exiting with the signal's code, and the supervisor waits for the bridge before it exits: Ctrl+C and `claude-wow service stop` strand nothing.
- **Permissions:** a refused tool (Claude's `permission_denials` in the result, a Grok `tool_call_update` whose status says so) is turned into an allowlist rule (`Bash(<first word>:*)` or the tool name, in Claude's syntax for every agent) and sent along as `denied`; an `allow=` flag on a later message merges them into that agent's `allowedTools` in `config.json`, including through the reload outbox. Codex has no allowlist: a `command_execution` it declined is named at the end of the reply instead.
- **Game context:** the latest context field received is kept in `state.json` (`context`), an empty one clears it. While one is held and `gameContext` in the config isn't `false`, every run gets two things. The system prompt, `protocol.systemPrompt(context, primer)` (as `--append-system-prompt` for Claude and Grok; at the top of the prompt, marked as context, for Codex, in full on a new session and without the primer on a resumed one), holds only what never changes within a chat: the reply rules, the plugin's lines, what the situation block and the `[Name]` links and the "Linked from the game" block mean, how to mark the map and hand over a macro, and the addon/macro primer (`primerFile`, default `docs/WOW-ADDON-PRIMER.md`); the context's presence turns those on, its text is not in it. The message, `protocol.messagePrompt(text, context, { image })`, opens with the context lines as a marked situation block (and the vision paragraph when a screenshot is attached), then the player's text. The split is deliberate: Claude Code records a conversation's system prompt on its first request and resumes with that record verbatim (`--system-prompt-snapshot`, on by default), so a context appended there was frozen at the chat's first message, and prompt caching is prefix-based, so anything that changes between messages (coordinates change with every step) must come after everything that does not. No context, nothing appended, primer included, and the message is exactly the text.
- **Transcripts:** every prompt and reply (with the agent that wrote it) is appended to `transcripts.json` per chat. The first message from an unknown session token means the addon's saved data is fresh, so the next three publishes carry a `restore` bundle (the 16 newest chats, 40 messages each) addressed to that token; the addon imports chats it doesn't have. The addon itself has no chat limit.
- **Publishing:** final results immediately; progress throttled to one write per 3 s.

`supervisor.js` restarts the bridge 3 s after any exit and is the `claude-wow` command. `npm start` / `start.ps1` run it in the current terminal; `start-window.cmd` opens its own console window (a `.cmd` running inline would make Ctrl+C trigger cmd's "Terminate batch job?" prompt). `service.js` behind `claude-wow service` makes it a per-user background service (LaunchAgent, systemd `--user` unit, or a Startup-folder launcher), with the supervisor writing the bridge's output to a rotating log and a pid file when `CLAUDE_WOW_SERVICE=1`; `bridge.log` is rotated by the supervisor too, which is safe because the bridge reopens it for every line. A service installed from a binary under `~/.claude-wow/releases/` runs `~/.claude-wow/current/claude-wow`, a symlink that `claude-wow dev deploy` and `dev rollback` move (`deploy.js`, `releases.js`): a deploy builds a release, waits until `state.json` has no `inflight` run, no `queued` message and no plugin `handling` entry, or no bridge holds `bridge.lock` (`idle.js`), marks `deploy.lock` as `switching` (the bridge holds new messages while that mark is live and keeps them in `state.json` `held` across the restart; it also keeps its last finished replies in `state.json` `replies` and publishes them again at start) and checks idle again, renames a new symlink over `current`, restarts the service through `service.js`, runs setup, and prunes old releases last. See [MIGRATE-PROD-INSTALL.md](MIGRATE-PROD-INSTALL.md). The release binary updates itself (`selfupdate.js`): the bridge checks the latest release once a day, verifies the download against `SHA256SUMS` and renames it over its own file (a running process keeps its old inode; Windows renames the running `.exe` aside first; under the `releases/` layout it calls `releases.js` `installAndActivate` to add `releases/<version>/` with `release.json` `"source": "self-update"` and flip `current`, so `dev rollback` can go back; a release whose `release.json` source is not `release` or `self-update`, such as a dev deploy, is never self-updated). The restart is the bridge's own decision, because only it knows its runs and queue: it writes nothing for the supervisor to poll, and exits with code 75 when nothing runs or waits and the game is closed or quiet; the supervisor starts the binary again at once. `update.json` in the home folder records the check and the pending restart, and a restart that did not bring the new version is not retried until the next update. The deploy's idle wait also reads `factory/runs.json`: a `running` run whose process is alive keeps a running bridge busy, so a deploy never restarts the bridge under a factory run. With `autoDeploy` set, a bridge that the macOS service runs from a `dev deploy` release starts that deploy itself (`autodeploy.js`): every 5 minutes, while `bridgeIdleStatus` is idle and no live deploy holds `deploy.lock`, it fetches `origin/<branch>` in the configured checkout; the first check only records the commit in `autodeploy.json`; when the branch later moves to another commit, it records it and spawns `/bin/sh` detached (its own session and process group, so the service restart the deploy causes does not end it before setup runs), which runs `<home>/current/claude-wow dev deploy <commit> --timeout 7200` and writes its exit code back to `autodeploy.json`. A failed exit, or a deploy that could not start (127), is added once to the next coding-chat message for that checkout. A `runs.json` that cannot be read counts as busy.

The bridge runs on Node or on Bun, and ships as one self-contained binary per platform built with `bun build --compile` (`build.js`, `build/entry.js`): the bridge, setup and the service commands with Bun's runtime inside, nothing to install first. Two things differ inside that binary, and `runtime.js` is the one place that knows them. `process.execPath` is the bridge itself, not an interpreter, so "run bridge.js with this node" becomes "run this binary with a subcommand" (`claude-wow bridge`, `claude-wow setup`, `claude-wow install-slots`, which the supervisor maps back and runs in-process), the service definition is the binary alone, and a JavaScript launcher an agent CLI ships (npm's `codex.js`) is run with the node found on the `PATH`. And the sources are inside the binary, so the files it hands to other programs by path, the capture scripts (spawned with python3 or PowerShell), the addon (copied into the game), `config.example.json`, the primer and the `claude-wow` Claude Code plugin (handed to Claude with `--plugin-dir`), are embedded at build time and written out under `~/.claude-wow/assets` on first use (`assets.js`), rewritten whenever the embedded copy differs. From a checkout every path is the checkout's and nothing is written. Config, state and logs are found through `CLAUDE_WOW_HOME` either way.

## Addon

`ClaudeWoW.lua` is a single file; sections in order: helpers, reload fallback, pixel strip, signals and slots, game context and links, sending, chats, rendering, UI, slash commands, events. `tests/addon_test.js` runs it in a Lua VM with a stub client (`tests/wow_stub.lua`) through a whole session: login, hello, a message decoded off the strip, a slot reply, Allow, restore.

- **Chats:** `db.chats[]` with id, name, cwd, agent (empty = the bridge's default), history, pendingId, unread, draft. A chat named `Chat N` takes its title from the first message. Deleting the last chat resets it instead. History entries are `{ role = "user"|"assistant"|"system", text, id, t, agent }`; entries saved as role `claude` by older versions are read as assistant replies from Claude.
- **Transcript:** a scroll frame of message bubbles (colored label per role, plus an accent bar on the dark theme only, timestamp, wrapped body); clicking a message opens a copy box, since FontStrings can't be selected. A left click on a web link in it asks the bridge to open the link in the browser when the bridge offers it ([Open link records](#open-link-records-kindurl)); a right, Ctrl or Shift click opens the copy box with the link. The working bubble shows elapsed time, heartbeat counts and the latest progress lines.
- **Windows:** main frame at `HIGH` strata, so StaticPopups and the roll frame (`DIALOG`) draw above it. The X button (the only title button), Esc, `/claude hide` and its old names `mini`/`min`, and the key binding close it (`OnHide` sets `shown = false`). There is no minimized state and no floating bar: `Q.MigrateMiniBar` runs once (`settings.miniBarV2`), turns a saved `minimized = true` into a closed window and drops `minimized` and the bar position. Esc in the composer clears focus and closes the window; the draft stays in the box. A closed window at login stays closed, and one open at logout opens again unless whisper tabs are on. The status line has four states: Ready, Working... (elapsed), Reply waiting, and "Can't reach the bridge. Start it, then click Connect."; the status tooltip adds a hint and the cost, labeled "Estimated API cost". Folder, agent, plugin, mode, pending message ids, slot polls and slot problems are in `/claude diag`. Rename, folder, agent and plugin `StaticPopup`s, and `CLAUDEWOW_DELETE`/`CLAUDEWOW_CLEAR` confirms. The menu that opens when a chat row is right-clicked (Rename..., Folder..., an Agent radio list from the agents the bridge reports or the Agent... prompt without one, Clear Messages, Delete) is one item list (`Q.ChatMenuItems`) drawn by `MenuUtil.CreateContextMenu` where the client has it and by a plain frame elsewhere, so both show the same items; the gear menu works the same way. A reply out of combat makes a sound, and one line on screen only when the window is closed and whisper tabs are off; with the minimap button hidden it also prints one chat line, `<agent> replied. Type /claude to open the window.` In combat it makes none of these.
- **Header buttons:** in the native window the project and MCP buttons sit right to left at the right end of the header band (`ClaudeWoWProjectButton`, `ClaudeWoWMcpButton`, built by `Q.HeaderButton`), and the chat title is anchored to the leftmost one shown, so it truncates first. `Cli.LayoutHeaderButtons` runs on every render and band resize: the buttons get the band less 16 px of title room and the gaps; when they do not fit, it drops the `Project:` label, then cuts the project name (down to 60 px), and only then hides MCP, so the two never overlap. The project button is capped at 240 px. Without native frames the same two sit along the bottom edge of the message box, clear of Send.
- **Effort meter:** `ClaudeWoWEffortButton` sits right above Send, as wide as Send and 16 px tall, and shows and hides with it. `Cli.UpdateEffortButton` draws five rising bars (`Cli.EffortBars`, color textures 4 to 14 px tall), gold up to the level and dim after it, with the value word to their left; `Cli.LayoutEffortWord` drops the word, never the bars, when it does not fit. The value is `Cli.EffortState`: `effortLock` for the chat's agent, else the chat's own `--effort`, else the bridge's `efforts[plugin][agent]`, else `auto` (the agent decides); it never says "default". An agent the bridge lists without effort, or a live-session chat, gets grey bars, no word, a disabled button and a tooltip saying so. An old bridge sends no `efforts`, so the meter shows `auto` and stays enabled.
- **Minimap button:** `Q.BuildMinimapButton()` runs at `PLAYER_LOGIN` after `BuildUI()`: a 31 px `ClaudeWoWMinimapButton` on `Minimap` (`MEDIUM` strata, level 8), laid out like LibDBIcon-1.0 (minor 55) without the library. The icon is `MinimapIcon.tga`, a 64x64 32-bit TGA of the orange Claude spark on a transparent background, drawn by `node dev/make-minimap-icon.js` (`--preview <png>` also writes a preview); when `SetTexture` reports the file missing (a client not restarted since the file was added), `Q.SetMinimapIcon` uses `Portrait.tga` made round with the `TempPortraitAlphaMask` mask. `MiniMap-TrackingBorder` is the `OVERLAY` layer, above the `ARTWORK` icon, and `UI-Minimap-Background` is `BACKGROUND`; `UI-Minimap-ZoomButton-Highlight` is the highlight. Sizes follow LibDBIcon: the Mainline layout when `WOW_PROJECT_ID == WOW_PROJECT_MAINLINE` (border 50, background 24 and icon 18, both centered), else the classic one (border 53, background 20 at `TOPLEFT` 7,-5, icon 17 at `TOPLEFT` 7,-6). As in LibDBIcon, the icon shows a 5% texcoord inset at rest and the full texture while the mouse is down or a drag runs (`Q.UpdateMinimapIconCoord`), so a press reads as a push. Left-click calls `ToggleWorkspace`, right-click `ShowOptions`. A left-button drag sets an `OnUpdate` that turns the cursor into an angle around the minimap center (`GetCursorPosition` over `Minimap:GetEffectiveScale()`), saves it as `ClaudeWoWDB.settings.minimapAngle` (account-wide, 225 by default), and places the button 5 px outside the edge; `GetMinimapShape()` picks, per quadrant, a round edge or a square one clamped to the box, with LibDBIcon's shape table (an unknown shape is round). The tooltip (`ANCHOR_LEFT`) has the product name, the plain status (`Q.PlainStatus`), a gold line with the new replies and working agents of the listed chats (`Q.ActivityText`, none when both are 0), `Q.StatusTooltip()` for the hint and cost lines, and green click hints. `Q.BuildMinimapSignal` adds what the old mini bar showed: an 8 px status light at `BOTTOMRIGHT` -2,2 on `OVERLAY` sublevel 7, above the ring, with the friends-list status icons of the window light (`ClaudeWoW.UpdateDot` sets both); and a glow, the `UI-Minimap-ZoomButton-Highlight` texture in `ADD` blend over the button. `Q.UpdateMinimapSignal` (from `UpdateStatus`, `Notify` and the window's `OnHide`) sets `button.signal`: `reply` while a listed chat has an unread reply and the window is closed (the glow pulses, an alpha loop from 1 to 0.15 over 0.8 s each way), `working` while an agent works and the window is closed (a steady glow at 40%), else `idle` (no glow). Both are textures of the button, so they hide with it. `settings.minimap` (on by default; `/claude config minimap`, the Options checkbox) only shows or hides it. Nothing in it is protected, so it works in combat.
- **Game context and links:** `GameContext()` asks the client about the build, character, zone, money, talents and skill lines, each call wrapped so a missing API just leaves its line out. `ExpandLinks()` rewrites `|H…|h[Name]|h` links in a message before it is sent (see the record format above). Shift-clicked links reach the addon's input box through a `hooksecurefunc` on `ChatFrameUtil.InsertLink` (the Forever client uses the modern chat code; every shift-click, from bags, spellbook or quest log, ends there; the old `ChatEdit_InsertLink` global is hooked instead only where the new one is missing), which only inserts when that box has keyboard focus, so shift-click elsewhere keeps its normal meaning.
- **Game chat:** by default only the reply's `TL;DR:` block is printed under `[Codex · name]` (whichever agent answered): the system prompt asks every agent to end its reply with one, `protocol.splitSummary` pulls it out in the bridge, and the slot record carries it as `summary` next to the full `text` (without one the addon prints the reply's first two lines). The workspace transcript draws the reply without that closing block (`Q.StripSummary`): it hides the last line-start TL;DR marker and everything after it when that block has at most 3 lines and 400 characters and the marker is outside a code fence (``` or ~~~ of any length, closed only by the same character at least as long). The addon keeps `summary` (up to 400 characters) on the history entry; when it is there the block must equal it, and entries without it (restored from the bridge, or from before this change) use the marker rule alone. The bubble's copy box keeps the whole text. A chat with no user or agent message shows an empty state (`Q.EmptyState`: restoring, not connected, or how to start plus the project): centered with a title when the chat has no messages at all, and only the hint line under the system lines when it has some. Setting a chat's project (`--project`, `#name`, the project button) is never written to the transcript (`Cli.Note`): it goes to the chat's tab (not while the window is open, whose header shows the project), or to the game chat when whisper tabs are off. `/claude config echo full` prints the whole reply line by line instead. Both come with `[reply]`/`[open]` hyperlinks. Every link the addon writes is an `addon:` link (`|Haddon:claudewow:<action>:<args>|h`): the client's own `LinkTypes.AddOn` handler takes it, so `SetItemRef` returns without opening the item tooltip, and a `hooksecurefunc("SetItemRef")` post-hook reads it (`ClaudeWoW.OnLink`; the older bare `claudewow:` links still in a chat log are read the same way). The actions are `open`, `reply`, `resume`, `connect`, `cancel`, `send`, `roll`, `macro`, `url` and `map`. `/claude -c <text>` sends to the current chat and `/claude <text>` starts a new chat and sends there (bare `/claude` opens the workspace window on the current chat, `/claude new` starts an empty chat); the old `/wow-ai`, `/ai`, `/ask`, `/wowai` and `/wow-claude` are gone. For both, a line whose first word is a subcommand only runs it when the rest fits that subcommand (nothing after `delete`, one word after `agent`, `on`/`off` after `context`), so `/claude delete the unused imports` is a message. Nothing of the game's chat code is replaced, because any line typed through an addon-replaced function runs tainted and a protected command on it (`/cast`, `/gquit`) is blocked. One seam carries everything: the `ChatFrame.OnEditBoxPreSendText` callback on `EventRegistry`, which the game's `SendText` fires after `ParseText` has run every slash command and before it reads the text and sends, through `securecallfunction`, so the addon's taint ends with the callback. No edit-box method is hooked, not even with `hooksecurefunc`: on 1.60.1.70124 the wrapper `hooksecurefunc` put in `ChatFrame1EditBox.UpdateHeader` called a nil, so every chat open, chat type change and Esc raised an error. `/r` uses the game's own reply: when a reply lands, `ClaudeWoW.Notify` calls `ChatFrameUtil.SetLastTellTarget("<Agent> [<chat>]", "WHISPER")` (type-checked, in a `pcall`, only when the pre-send callback is registered). The name has a space and brackets, so no player can have it. The game's `/r` (`ProcessChatType`'s `REPLY` branch, or the reply key's `ChatFrameUtil.ReplyTell`) then sets the box to a whisper to that name and `UpdateHeader` draws "To Claude [chat]:" itself; Enter fires the pre-send callback, which maps the name back to its chat (the addon remembers which chat each offered name belongs to, so the one that replied last wins, and a renamed or deleted chat's name is still swallowed) and empties the box, with whisper tabs on or off. A real whisper makes the game put its sender first again, so `/r` goes to whoever messaged last. The addon's write taints the entries of the game's last-tell list, so a `/r` line runs tainted from the moment it reads the list; that line only reaches `SendChatMessage`, which is not protected, and a secure command (`/cast`, `/gquit`) is run by `ParseText` before anything reads the list or the box's attributes.
- **Whisper tabs (on by default, `/claude config ui whisper on|off`):** the tab is the everyday interface and the window is the workspace. Each chat gets a temporary chat window (`FCF_OpenTemporaryWindow("WHISPER", <agent>, ...)`, retitled to the chat's name, or to the agent's while the chat keeps its default name): the active chat's at login, once the bridge has named its agent (or after 15 s), and any other chat's on its first message or command. A tab whose whisper target no longer matches the chat's agent is closed and opened again under the new name. Replies of up to 8 lines and 700 characters are written whole; longer ones show the `summary` (TL;DR) lines and a `[full reply]` link. The progress line (`Claude is working... 45s · 12 actions - <bridge text>  [cancel]`) and the bridge status line are "live" lines: the addon removes its previous copy with the frame's `RemoveMessagesByPredicate` (Blizzard exposes it on `ScrollingMessageFrameSecureMixin` for addons, as an elevation barrier) and adds the new one, so each stays one line; a frame without it gets at most one progress line per 20 s. Denials add `[Greed] [Need] [Pass]` links (or `[Allow once] [Allow & retry] [Pass]` with the roll off; `[Greed] [Pass]` only in a live chat, where nothing is saved). Need and Allow & retry go through `ClaudeWoW.ConfirmAllow`, the one path to a saved rule: it opens the `CLAUDEWOW_ALLOW_ALWAYS` dialog, parks the roll (its timer stops), and on Always Allow checks again that the chat's open denial has the same message id and rules before it grants; Cancel puts the roll back, macros a `[Create Macro: Name]` link that opens the `CLAUDEWOW_MACRO` prompt, map layers a `[show route]` link (`ClaudeWoWMap.ShowLayer`, `OpenWorldMap` outside combat). Slash commands typed in a tab answer in that tab (`Cli.Begin`/`Cli.Finish` wrap each `/claude` call and route the system lines it added), typed in the game chat they answer there, and neither opens the window. Existing installs: `whisperV2` moves a saved `whisper = false` to on once and says so in the tab, unless the chat history's last whisper toggle was "Whisper tabs are off", which is kept as an explicit choice (`whisperChoice`). The addon composes the lines itself (`[Claude] whispers: ...` in `ChatTypeInfo.WHISPER`, `To Claude:` in `WHISPER_INFORM`, progress in `SYSTEM`) through the frame's `AddMessage`, because this client has no `ChatFrame_MessageEventHandler` global to feed a fake event to, and flashes the tab with `FCF_StartAlertFlash` when it isn't the selected one. Sends go through the pre-send callback: a box whose chat type is `WHISPER` and which belongs to a chat's tab, or whose whisper target is an agent's name (`/w Claude ...` typed anywhere, which the game's own parser has already turned into a whisper by then), is emptied and its text handed to `ClaudeWoW.Send`; the game then finds nothing to send and resets the box as after any send. A slash command typed in a tab is the game's to run, as anywhere else: `/cast` works, and `/claude -c ...` applies to that tab's chat. Without the callback (a client with no `EventRegistry`) no tab is opened. A `CHAT_MSG_SYSTEM` filter (installed at login whatever the setting) turns the server's "No player named 'Claude'" (or a `/r` name, "Claude [chat]") into a red LEAK line and counts it, so a send that got through is visible rather than mistaken for the game's own message. While the setting is off no tab is opened and the pre-send callback only takes `/r` names; the window stays the record of the chat.
- **The workspace window (`Window.lua`):** per character (`ClaudeWoWDB.layouts["Name-Realm"]`, left/top/width/height in UIParent units, snapped to a screen edge within 16 px, clamped when the UI scale or the display changes; an older install starts from its account-wide `point`/`width`). It steps aside for Blizzard panels: `hooksecurefunc` on `ShowUIPanel`, `HideUIPanel`, `UpdateUIPanelPositions`, the bag toggles, `StaticPopup_Show`/`_Hide` and the world map's `Maximize`/`Minimize` schedule a relayout, and a 0.25 s poll of the watched frames' shown state (only while the window is up) catches anything else. The relayout measures the shown panels with `GetLeft`/`GetTop` scaled by their effective scale, and moves the window to the free spot nearest its home, or leaves it home when there is none. The world map (not maximized) is docked against instead (`W.MapDock`): when the map overlaps the window's home, the window goes 8 px right of the map (or left, when there is no room on the right) with the map's measured top and height, narrowed to fit the screen down to 560 px, so its top and bottom edges line up with the map's. A home blocked only by other panels while the map is open is a normal step-aside. Blizzard's classic_era UI source (not measured in the client) sizes the small map 610 x 438 with `UIPanelWindows` offsets `xoffset = -16`, `yoffset = 10`, which puts its edges away from the window's 780 x 500 home at `TOP_OFFSET`; the saved size is not changed, and the window goes home at its own size when the map closes. A map shorter than 300 px or no free place beside it falls back to the nearest free spot. One panel is handled the other way round: on Classic Era the loot window is a left panel (`UIPanelWindows.LootFrame.area = "left"`), so the game puts it in the slot the window holds. When `LootFrame` is shown at the slot (`LEFT_OFFSET`, `TOP_OFFSET`), `lootUnderMouse` is off and the frame is not protected, the window takes the spot it would take among the other panels (home when that is free) and moves `LootFrame` right of that spot, `PANEl_SPACING_X` away and on the same line, if that place is on screen and clear of the other panels; otherwise it steps aside as for any panel. Once moved, the loot window counts as an ordinary panel: resizing the window while it is open makes the window step aside from it, and closing the window leaves it where it is. The maximized map, the game menu and the settings hide it (`ClaudeWoW.Suspend`, which keeps `shown`) and bring it back when they close; a window the player opened or closed meanwhile is left as it is. It dims to `dim` (35%) on `PLAYER_STARTED_MOVING` and `PLAYER_REGEN_DISABLED`, fades back on the stop events, and is opaque under the mouse or while its input has focus; the fade is an `OnUpdate` on the addon's own driver frame, not `UIFrameFade`, so no shared Blizzard table is touched. Nothing here is secure or protected, so all of it works in combat, and no Blizzard frame is shown, hidden or given a script; the only one moved is that unprotected `LootFrame`. `Bindings.xml` adds the **Claude WoW: open or close the workspace** binding.
- **Reload fallback:** `ReloadUI()` needs a hardware event, a reload is asked for with a `StaticPopup` ("Reload needed", **Reload** / **Later**) shown once the interval has elapsed, in every mode, whenever a reload is needed to read a waiting reply (reload mode, or pixels or slots that can't work); the Reload click is the hardware event and the consent. It is never shown in combat (leaving combat re-arms it). `autoRefresh` only decides whether **Later** re-arms it after the interval (on) or it stays at one ask per waiting reply, keyed by the pending message ids (off). `autoRefresh` was turned off once (`autoRefreshV2`) for every install not in reload mode; a later `/claude config auto` choice is kept.

## Limits and known issues

- The client's saved-data wipe (observed on the beta) is outside the addon's control; recovery depends on the bridge having been running.
- 200 slots per UI session. Each reply costs one slot when the readiness signal works, about four otherwise; `/claude reload` resets the pool.
- A signal file fires once per game process. Slot numbers that wrap around within one session (every 200 messages) lose the cheap signals until the game restarts; self-detected, and replies still arrive through the slot schedule. The presence rings last at least 2000 beats (16.7 hours) per game process; after that the light uses the slower windows.
- Message capacity ≈ 3.2 KB per send; longer text is refused with a hint.
- Replies are published in full (a ~3 KB message can produce a 60 KB reply; that is fine for a slot file). The bridge-side transcript keeps the first 4000 characters of each message, and a restore sends back the last 40 messages per chat at 2000 characters each.
- Windows, Linux with the game under Wine on X11 (see [INSTALL-LINUX.md](INSTALL-LINUX.md)), or macOS with a native client (README, "macOS (native client)"; contributed and tested live by its author).
